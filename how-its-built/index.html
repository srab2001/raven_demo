2How the elements connect

Signing in with Google

  1. Middleware (middleware.ts) checks a signed session cookie on every request to a gated page. No cookie → redirect to /login.
  2. /api/auth/google/start redirects to Google's consent screen.
  3. /api/auth/google/callback exchanges the code, then verifies the ID token against Google's JWKS using lib/jwt.ts's verifyGoogleIdToken.
  4. The account is upserted into the users table. If approved, a session JWT is signed (also via lib/jwt.ts, Web Crypto only) into an httpOnly cookie.
  5. The browser is redirected back to the page it originally asked for.

Why it's built this way: approval-gated access means nobody sees a demo — let alone the admin panel — before a human explicitly approves them, and the session-signing code has zero third-party or Node-only dependencies so it runs identically in Vercel's serverless functions and its Edge Middleware.

Editing demo copy

  1. An admin edits a textarea on /admin and clicks Save.
  2. The browser sends POST /api/admin/content with { key, text }.
  3. requireAdmin() checks the session; api/admin/content.ts checks the key exists in lib/contentManifest.ts.
  4. The row is upserted into content_overrides.
  5. Every demo's ContentProvider fetches /api/content on load and re-renders any callout or tooltip whose id matches an override.

Why it's built this way: copy changes ship without a code deploy, but only an approved admin can make them, and the read side (/api/content) stays public because it's non-sensitive UI text for pages already gated by middleware.

The exact path a save takes

  1. fetch('/api/admin/content', { method: 'POST', body: JSON.stringify({ key, text }) })
  2. Server validates: is there a session? is it an admin? does key exist in the manifest? is text non-empty?
  3. INSERT ... ON CONFLICT (key) DO UPDATE into content_overrides.
  4. The iframe's demo re-fetches /api/content next time its ContentProvider mounts (reload the iframe after saving to see it immediately).

The bigger one: a production crash, and the actual fix

Shortly after Google sign-in first shipped, production started returning FUNCTION_INVOCATION_FAILED on auth routes — even though the Vercel build itself said "Ready." The full incident is written up in docs/LESSONS-LEARNED.md. Short version:

- import { SignJWT } from 'jose' // ESM-only; broke under Vercel's monorepo Node bundling
+ // lib/jwt.ts rewritten to use only Web Crypto (crypto.subtle) —
+ // works identically under CommonJS or ESM, and also runs in Edge Middleware,
+ // which has no node:crypto.

How it was actually fixed: not by tuning package.json's "type" field further (that looked like it worked, then the same crash came back on the next fresh deploy) — by removing the ESM-only dependency entirely and verifying the fix by compiling and inspecting the emitted JS, plus unit-testing the new sign/verify code directly.
